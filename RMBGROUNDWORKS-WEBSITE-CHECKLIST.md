## 3. Customer needs and decision journeys

The following is **research-led interpretation**, to validate with RMB. A foundation package buyer and a person arranging a small external-works job need different levels of detail.

| Audience | Trigger and questions | Evidence needed | Proposed journey and action |
| --- | --- | --- | --- |
| Developer / main contractor / quantity surveyor | A package needs pricing or a dependable subcontractor. Can RMB handle this scope, programme and site? | Comparable works; clear package boundaries; coordination approach; verified capability documents | Search/referral → relevant service → matching case study → tender/project enquiry with scope, location and target dates. |
| Commercial property / facilities manager | Car park, drainage or external works must be planned around an occupied site. How will access and disruption be managed? | Comparable completed surfaces/drainage; phasing/access explanation; scope and handover evidence | Service landing page → relevant project → process → discuss survey/quotation. | Public sector / appointed contractor | A supplier must satisfy procurement, communication and safety requirements. Can RMB provide suitable evidence? | Verified policies/certificates where available; relevant authorised project references; clear tender contact | Search/referral → capability/about → service + case study → tender enquiry. | Returning client / referred visitor | Already knows RMB and needs contact details or proof to forward internally | Recognisable brand, direct email/phone and easy project links | Header contact/phone → short enquiry or direct call; avoid forcing a long discovery journey. |

### Case study

- [ ] Record a permitted title/location, sector, project status, services and RMB's actual role.
- [ ] Describe the challenge, relevant constraints, approach and evidenced outcome; distinguish completion from work in progress.
- [ ] Curate original overview, working-stage, detail and completed-work images where available.
- [ ] Identify project photos correctly; adjacent gallery photos must not be assumed to show the same job.
- [ ] Publish client names, dates, contract values and results only when confirmed and permitted.
- [ ] Add a relevant service link, related work and “Discuss a similar project” action.
- [ ] If case-study facts are unavailable at launch, use honest gallery captions and service labels rather than inventing case studies.

### About and capability

- [ ] Tell the real company/team story after interviewing RMB or receiving an approved brief.
- [ ] Explain delivery coordination, site review, quotation and quality/sign-off practices as confirmed by the team.
- [ ] Publish verified documents selectively and keep their expiry/review dates manageable.
- [ ] Replace broad “trusted”, “safe” and “on time” claims with specific evidence wherever possible.

### Contact and enquiry

- [ ] Offer intent choices such as **project enquiry** and **tender enquiry**, with appropriate follow-up guidance.
- [ ] Keep required inputs proportionate: name, one usable contact method, project location and short scope; company, service and target dates can be optional where appropriate.
- [ ] Use visible field labels, autocomplete, sensible mobile keyboards and clear required/optional cues.
- [ ] Provide direct telephone/email alternatives and confirmed opening hours.
- [ ] State what happens next using an approved process; avoid an invented “24-hour response” promise.
- [ ] Show sending, validation, accepted submission and delivery-failure states; preserve entered text after a recoverable error.
- [ ] Show success only after the server accepts the enquiry; verify delivery separately before launch.
- [ ] Add appropriate server-side validation, anti-spam controls and rate limits; keep keys and recipients server-side.
- [ ] Decide how tender drawings/documents are handled. Prefer an approved email route initially if secure uploads are unnecessary.
- [ ] Approve recipient, retention, privacy notice and failure handling before connecting the form.

## 8. Animation and interaction specification

These are proposed design parameters, not implementation commitments or measured existing behaviour.

| Element | Proposed motion | Mobile / reduced-motion treatment |
| --- | --- | --- |
| Initial hero | Restrained fade and 16–24px text reveal, roughly 500–700ms; image visible immediately | Keep content readable immediately; remove translation/scale when reduced motion is requested. |
| Section entrances | One-time opacity/short translate, roughly 350–550ms, small stagger | Reduce or remove stagger; content remains visible if scripts fail. |
| Project imagery | Subtle 1.02–1.04 hover scale and caption/arrow feedback, roughly 250–400ms | No essential hover-only information; touch has direct visible actions. |
| Navigation/buttons | Colour/underline/focus feedback, roughly 150–250ms | Equivalent keyboard feedback; avoid delayed activation. |
| Optional project hero slides | Manual-first, clear arrows/count and optional explicit play control | Static first image in reduced motion; stop rotation on focus/interaction and provide pause if autoplay is introduced. |
| Gallery lightbox | Short fade, caption, previous/next and close controls | Keyboard operable, Escape closes, focus contained and restored; tap alternatives to dragging. |
| Process | Subtle sequential emphasis as steps enter view | Full process readable without animation or horizontal pinning. |

- [ ] Choreograph a few important elements per viewport; avoid animation on every component.
- [ ] Animate transform/opacity where practical and profile actual devices; do not assume smoothness from desktop preview alone.
- [ ] Use natural scrolling. No scroll hijacking, mandatory horizontal storytelling, custom cursor or mouse-following CTA.
- [ ] Keep motion out of form entry and error recovery.
- [ ] Avoid a blocking loader. Fonts, photographs and essential copy must not wait for an intro sequence.
- [ ] Build reduced-motion behaviour from the first prototype; changing the preference while open should leave the page usable.
- [ ] Retain visible fallback content when JavaScript, an animation library or an observer fails.

## 9. Proposed technical approach — for the later build

**Recommendation: Astro with TypeScript, pre-rendered service/project pages, scoped design tokens and small interactive components only where needed.** This suits a photographic content-led contractor website. [Astro's islands architecture](https://docs.astro.build/en/concepts/islands/) supports static HTML with selective JavaScript for interactive areas. The current site's public HTML also contains Astro asset paths and Astro analytics integration markers; the empty new repository does not contain that source code.

- [ ] Confirm content-editing ownership before choosing a CMS. Start with structured local content if updates are developer-managed; avoid adding a CMS account by default.
- [ ] Keep brand tokens, shared page templates, service content and project content structured consistently.
- [ ] Use CSS/native browser motion for simple effects; add a focused animation library only if a reviewed interaction needs it.
- [ ] Generate responsive image variants, set dimensions and prioritise the hero; lazy-load lower-page photography.
- [ ] Keep original masters separate from display derivatives; preserve captions, alt text and crop focal points.
- [ ] Use a real server-side form endpoint suited to the chosen host; do not assume an inherited endpoint or email provider will transfer.
- [ ] Select hosting and deployment settings after the plan is accepted and existing domain/DNS/hosting arrangements are known.
- [ ] Keep preview builds separate from production and prevent previews from entering search results.
- [ ] Confirm domain, redirects, secrets, submission handling, monitoring and rollback before any launch.

## 11. Quality and acceptance checks for the future website

These are targets to test during the later build. Research has not established the current site's Core Web Vitals or accessibility conformance.

- [ ] Review home, service, project index, case study, contact and error states at 360, 390, 768, 1024 and 1440px widths, plus 320px reflow and landscape where relevant.
- [ ] Check current Chrome, Edge, Safari and Firefox, including real iOS/Android sampling where available.
- [ ] Test long titles, captions, validation errors, empty project filters, missing images and direct route loads.
- [ ] Aim for WCAG 2.2 AA and verify semantics, skip link, logical headings, keyboard access, visible/unobscured focus, labelled controls, alt text, contrast, reflow and status announcements. Use [W3C's reference](https://www.w3.org/WAI/WCAG22/quickref/) alongside manual checks.
- [ ] Use comfortable touch targets around 44px where practical; test close, menu, carousel and lightbox controls with touch and keyboard.
- [ ] Confirm menus/lightboxes close correctly, restore focus and do not trap users unintentionally.
- [ ] Check reduced motion, disabled JavaScript, slow loading and failed submission paths.
- [ ] Target good field Core Web Vitals at the 75th percentile when enough data exists: **LCP ≤2.5s, INP ≤200ms, CLS ≤0.1**. Use [Web Vitals guidance](https://web.dev/articles/vitals). Lab checks are prelaunch diagnostics, not a field pass.
- [ ] Set practical initial budgets to review in prototype: appropriately sized hero around 250–400KB where visual quality allows, and roughly ≤100KB compressed first-party JavaScript per normal content page. Document justified exceptions instead of damaging imagery to hit an arbitrary number.
- [ ] Verify phone/mail links, all main journeys, project filters, lightbox, redirects, SEO metadata and form acceptance/delivery with a controlled test before launch is authorised.
- [ ] Run suitable build/type checks, link checks, automated accessibility sampling and manual visual review; fix material issues and record any remaining limits.
